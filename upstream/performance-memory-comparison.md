# Original versus current Rust: extension memory and batching

Current follow-up: original internal query splitting and preliminary merging are now implemented, including chunk-local masks/statistics and skipping the unused full-query lookup. Protein preliminary DP scratch and CBS matrix rows now persist for the original search lifetime; nucleotide OID-batch subject restoration and range-only formatting also reuse buffers. All1,259 real HSPs remain exactly equal to the original core, and default large-query split cases match the CLI. The observations below retain their earlier artifact context; they are not current timing or allocation measurements. The adaptive batch-size controller is translated as an explicit utility; the prepared-batch library does not add hidden file batching. No bumpalo or new arena was introduced.

Read-only audit of pinned BLAST+ **2.17.0+**, 2026-11-13. The current Rust source includes persistent nucleotide gapped scratch, partial translated-target caching, the safe amino-acid scanner span changes, and release ThinLTO/codegen-units=1. No algorithm, allocator, or production Rust changes were made for this audit. Disk/v5 persistence is outside the user's current requested scope.

## What the measurements actually established

The earlier accurate staphylococcus megablast profile sampled 10 child invocations of the then-current ThinLTO binary, SHA-256 `5060915728d7d55203fe7535d468e66592aab2db7952d5e3f7e8812396ab2183`. It had 834 samples, none lost: `memset` accounted for 46.05% of self samples. A resolved call chain specifically attributed 17.88% of total samples to `mb_space_new -> s_blast_greedy_align_mem_alloc -> blast_gap_align_struct_new`; 16.11% was beneath the preliminary-subject-chunk caller. Unresolved `memset` stacks do **not** establish that the entire 46.05% came from this pool. Evidence: `/tmp/btyper-current-staph-mega.perf.data`, `-flat.txt`, `-callgraph.txt`, and `/tmp/btyper-current-profile-build.json`.

That profile predates the scratch-lifetime correction. Current [nucleotide_setup.rs](../src/nucleotide_setup.rs#L265) constructs scratch once with the database maximum sequence length, retains it in the search owner, and rebinds its matrix borrow across preliminary subjects/chunks and traceback (lines397–434,489–528,541 onward). Owned buffers move without moving their allocations. Original [blast_setup.c](../vendor/ncbi-blast-2.17.0+-src/c++/src/algo/blast/core/blast_setup.c#L989) also initializes search scratch from the database maximum length; it does not recreate a 12MB greedy pool per subject. This was a concrete lifetime mismatch, now fixed. The old samples cannot establish the remaining allocation fraction in the final binary.

The later yeast tblastn profile of that same pre-scratch-fix artifact had 3091 samples, none lost: AA small scanner43.10%, AA two-hit extension19.34%, semi-gapped DP7.58%, FASTA reading5.87%, traceback DP3.98%, compressed translation2.60%, Cholesky1.93%, general translation0.55%. Thus a general-purpose arena is not supported as the next tblastn fix by those samples. The earlier whole-frame translation bottleneck had already disappeared after restoring original partial-target caching. Safe scanner changes landed afterward; their remaining cost needs fresh measurement.

| Greedy pool | `MBSpaceNew`, `greedy_align.c:43–65`: minimum1,000,000 cells, linked blocks, bump offset | [greedy_align.rs:28–71](../src/core/greedy_align.rs#L28): same minimum/block growth/bump/reset behavior, stable owned buffers | Already the original specialized arena, not one heap allocation per diagonal/cell. Minimum payload12,000,000 bytes. |
| DP cells | `BlastGapDP`, `blast_gapalign.h:57`: two `Int4` fields | [blast_dynamic_align.rs:19](../src/core/blast_dynamic_align.rs#L19): two `i32`, `#[repr(C)]` | Same 8-byte cell stride. |
| Traceback-byte arena | `s_GapGetState`, `blast_gapalign.c:61–138`: minimum2MiB, request plus one third, reuse or replace unused blocks; purge resets used count | [blast_dynamic_align.rs:70–105](../src/core/blast_dynamic_align.rs#L70): same geometry and decisions, stable arena indices replace linked pointers | Already reusable; allocating a replacement arena would duplicate this mechanism. |
| DP row growth | `blast_gapalign.c:460–468,641–648`: maximum(required+100, twice previous), `malloc`/`realloc` | [blast_dynamic_align.rs:147–149,279–284](../src/core/blast_dynamic_align.rs#L147), corresponding semi-gapped paths | Same requested logical sizes/growth; Rust initializes newly exposed storage. |
| Row descriptors | Greedy row pointer8 bytes; traceback row pointer8 bytes, on ordinary64-bit targets | Greedy pointer+two bounds typically16 bytes; traceback `{block,start}`16 bytes | Additional row metadata and address/bounds work, not doubled cell payload. Potential hot-loop cost requires current assembly/profile evidence. |

The last row's sizes describe ordinary64-bit layouts, not a measured cross-platform ABI guarantee. C `SMBSpace` metadata is typically24 bytes versus Rust40; C traceback-node metadata typically24 versus Rust32. These few bytes per million-cell/2MiB block are negligible relative to payload. Rust's contiguous vector of traceback-node descriptors can improve descriptor locality; payload buffers remain separate and stable, as in C.

**Initialization is still different.** The large C greedy pool uses `malloc`, **not `calloc`** (`greedy_align.c:54`). C DP byte blocks also use `malloc` (`blast_gapalign.c:82,97,109`). Rust uses initialized vectors (`greedy_align.rs:37`, `blast_dynamic_align.rs:78,87,95`). C does not request zeroing of unused cells; Rust ensures initialized values. Some C auxiliary arrays do use `calloc` (`blast_gapalign.c:240,248`), so a blanket explanation based on `calloc` and lazy pages is inaccurate. Allocator/compiler/OS choices determine whether Rust zero initialization becomes `calloc`, explicit `memset`, or demand-zero storage. Source alone does not establish current page-fault or bandwidth cost. Lifetime reuse now amortizes initialization over the search; first allocation, block growth and search-owner reconstruction can still pay it.

Rust additionally checks greedy row bounds ([greedy_align.rs:89–101](../src/core/greedy_align.rs#L89)), sequence slice accesses and arena indexing; C accesses validated pointers directly. Those checks can leave branches, address recomputation or register spills even with identical recurrences. They are a plausible remaining difference, not evidence for changing arena ownership or using unchecked/uninitialized storage. Current release ThinLTO enables cross-module visibility; emitted-code comparison should precede inline annotations or further span hoists. DP traceback row tables remain temporary per alignment in both versions (`blast_gapalign.c:449–450`, Rust lines140–141); converting them to persistent buffers would be an additional documented lifetime adaptation, not restoration of an omitted original mechanism.

## SIMD, compiler selection and crafted source mechanisms

The pinned greedy and ordinary nucleotide/protein DP extension files contain **no explicit SSE/AVX/NEON intrinsics, architecture-selected kernel, runtime CPU dispatch, hardware-prefetch instruction, or custom aligned allocator**. The only conditional code in `greedy_align.c` concerns diagnostics; `blast_gapalign.c` likewise has diagnostic conditionals and inline helpers, not a SIMD alternative for the supported paths. Searching core sources/headers for intrinsic names and SIMD/CPU feature terms found no such alternative in these kernels. This finding is deliberately limited to the inspected core; it does not describe every toolkit component or compiler-generated machine instruction.

The actual crafted mechanisms are already material: zero-gap-cost greedy distance rather than generic quadratic DP; packed2na extraction; non-affine versus affine paths; distance/diagonal bounds; x-drop pruning; two-row reuse without traceback; million-cell bump pools;2MiB traceback arenas; and adaptive DP width/growth. Rust preserves those algorithms and geometry. `s_FindFirstMismatch` is marked `NCBI_INLINE` in C (`greedy_align.c:313`); Rust [s_find_first_mismatch](../src/core/greedy_align.rs#L239) has no explicit inline attribute, leaving the decision to LLVM/LTO. This is an inspectable code-generation question, not proof of missed inlining. C's sentinel check outside the match loop and compressed/uncompressed directional branches are preserved in Rust lines260–316.

Core AA scanner comments labeled “prefetch” (`blast_aascan.c:256,394`) mean an ordinary early character load/linked-cell pointer advance in the compressed-table branch, not an x86 prefetch intrinsic. That branch is not evidence of an omitted SIMD implementation for the default small-AA table. An allocator dependency such as bumpalo should not be added merely because it is an arena: these hot extension paths already have the original pools, stable addresses and source-specific purge semantics. A replacement would need a measured allocation hotspot, equivalent block lifetime/alignment, and parity evidence.

## Concrete missing source wrapper mechanisms: query working sets

The example currently reads the entire query FASTA into one `PreparedNucleotideBatch` or `PreparedProteinBatch` ([native_search.rs:102–106,144–148](../examples/native_search.rs#L102)). This explicit library API is reasonable for one core batch, but the original CLI bounds and adapts the input working set.

* `CBatchSizeMixer`, [blast_app_util.hpp:57–84](../vendor/ncbi-blast-2.17.0+-src/c++/src/app/blast/blast_app_util.hpp#L57), starts at5000 letters with minimum100 and target1,000,000 extensions. Its source update ([blast_app_util.cpp:65–81](../vendor/ncbi-blast-2.17.0+-src/c++/src/app/blast/blast_app_util.cpp#L65)) estimates `(hits+1)/batch_size`, mixes current/previous estimates with weights0.3/0.7, and clamps the next batch. Original real nucleotide oracle captures grouped7+1 queries while Rust used8; supplied results still matched exactly.
* `SplitQuery_GetChunkSize`, [local_blast.cpp:54–75](../vendor/ncbi-blast-2.17.0+-src/c++/src/algo/blast/api/local_blast.cpp#L54), selects classic1,000,000, megablast5,000,000, tblastn20,000 query letters. For these nontranslated query types the overlap is100 ([split_query_aux_priv.cpp:50–69](../vendor/ncbi-blast-2.17.0+-src/c++/src/algo/blast/api/split_query_aux_priv.cpp#L50)). The actual split count is `floor(total/(target-overlap))`; counts<=1 remain unsplit, otherwise chunk sizes are balanced (lines101–145). These target values are not simple hard split thresholds.

At the audit snapshot both wrapper mechanisms were untranslated; see the implementation follow-up above. Whole-batch lookup tables, query masks, context/diagonal metadata and retained candidate results can therefore exceed the original working set. The effect can be better amortization or worse locality/memory usage; it must be measured rather than presumed. Restoring source batching/splitting is preferable to inventing a different allocation policy, especially for many queries or genome-sized queries. Query-split result merging and context/statistical bookkeeping are correctness work too; subject chunking already present is a separate mechanism. C++ query-factory capabilities can disable splitting, so the comparison must identify the actual CLI/factory path.

## Next evidence and risk order

1. Profile the final artifact after persistent scratch and AA-span changes. Determine remaining zero-fill/page-fault cost before changing allocation. No fresh timing claim is made here while parent paired benchmarks run.
2. Translate the omitted original query working-set mechanisms if the supported tool scope includes arbitrary FASTA batches/long queries; compare equivalent grouping and report memory as well as elapsed time.
3. If greedy/DP remains hot, compare actual emitted C/Rust inner loops for residual bounds branches, repeated row-index addressing and failed inlining. Prefer source-preserving checked-span/hoist adaptations with complete kernel-output parity.
4. A custom allocator, new arena dependency, changed block geometry, uninitialized cells or speculative SIMD kernel is not justified by the current evidence. Changes to those mechanisms would introduce extra proof obligations and could obscure the original algorithm's performance design.

Strict original-core and CLI parity reports, and integrity-gated paired performance reports, remain authoritative; layout reasoning and historical samples alone establish neither final speed nor universal parity. Cross-platform workflow configuration is not evidence of green remote Linux/Windows/macOS runs.
