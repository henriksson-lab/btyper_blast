Current follow-up: original internal query splitting and preliminary merging are now implemented, including chunk-local masks/statistics and skipping the unused full-query lookup. Protein preliminary DP scratch and CBS matrix rows now persist for the original search lifetime; nucleotide OID-batch subject restoration and range-only formatting also reuse buffers. All1,259 real HSPs remain exactly equal to the original core, and default large-query split cases match the CLI. The observations below retain their earlier artifact context; they are not current timing or allocation measurements. The adaptive batch-size controller is translated as an explicit utility; the prepared-batch library does not add hidden file batching. No bumpalo or new arena was introduced.

Read-only comparison of pinned BLAST+ **2.17.0+**, 2026-11-13. No production code or algorithm changed for this audit. The memory hypothesis is plausible principally through extra address checks, metadata loads, stack spills and a remaining matrix-conversion lifetime mismatch. The hot lookup and DP **payload layouts already match C**. There is no cache-miss measurement here establishing a DRAM bottleneck.

## Memory representation really used

| Data | Pinned C | Current Rust | Implication |
|---|---|---|---|
| Small/ordinary AA lookup cell | 12/16 bytes | 12/16 bytes, explicit C-compatible representation | Same backbone footprint and stride. |
| Presence vector and overflow | Contiguous 32-bit words; small offsets 16-bit | Same element widths and geometry | No extra allocation per lookup hit. |
| Diagonal cell | Packed 31-bit last-hit plus 1-bit flag | Packed single `u32` | Same 4-byte cell. |
| Hit offset pair | Two 32-bit offsets | Two 32-bit offsets | Same 8-byte output record. |
| DP cell | Two 32-bit scores | Two `i32`, `repr(C)` | Same 8-byte cell. |
| Ordinary score matrix | Separately allocated rows and pointer array | Separately allocated rows and `Vec` descriptors | Same 3136-byte 28×28 score payload; Rust row descriptors add 448 bytes on this 64-bit target. |

Source locations: [lookup layouts](../src/core/blast_aalookup.rs#L20), [packed diagonal](../src/core/blast_extend.rs#L54), [DP layout](../src/core/blast_dynamic_align.rs#L19), and original `_PSIAllocateMatrix` in `blast_psi_priv.c:66–85`. The focused original-C lookup harness `/tmp/btyper-aa-lookup-c-check.c` confirms original 16/12-byte cells. C does **not** universally use one contiguous score-matrix allocation.

Default word 3 uses 28,540 backbone cells: 342,480 bytes for small cells, plus a 3568-byte presence vector. The yeast query batch's diagonal array has 4096 cells/16 KiB. On the profiled Xeon 6138, the lookup fits the 1 MiB L2 but exceeds 32 KiB L1D. Random backbone accesses can matter, but both versions have the same payload footprint. Matrix descriptor overhead alone is too small to justify a large-memory explanation.

## Ranked next investigations

1. **Reduce scanner checks and spills without changing table geometry or restart order.** This is the strongest hotspot-backed lead. Current [small scanner](../src/core/blast_aascan.rs#L86) already validates a subject span once and copies each hit run through bounded slices/zip; those changes removed subject/output checks from the inner loop. Final assembly still bounds-checks the presence-vector index on every scanned word, reloads the PV base from the stack, and checks the backbone index on a PV hit. Original pointer code has no corresponding bounds branches and retains the PV base in a register. Static function size is 1527 bytes Rust versus 960 bytes C; stack reservation 200 bytes versus C's red-zone use. Static `%rsp` references are 64 versus 37. These counts show more emitted stack-access instructions, **not measured dynamic memory traffic or cache stalls**. Both versions spill some values.

   Prefer safe proof-hoisting or a construction-validated scanner view, then inspect emitted code and run paired whole-workflow measurements. A mask-only proof is invalid: mask 32767 exceeds the 28,540-cell backbone. A tested explicit preguard did not persuade LLVM and enlarged the frame; it was rejected. A padded/constant-word trial removed checks but added approximately 3.5 KiB of copying per scan call and was also rejected. Do not reintroduce that per-call copy. A persistent prepared view would be a separate measured experiment. Any unchecked access would require a reviewed proof of alphabet, spans, index and capacity invariants; it is not necessary to begin with unsafe code.

2. **Carry validated spans into two-hit and gapped inner loops.** [Two-hit processing](../src/core/aa_ungapped.rs#L214) is the second sampled hotspot; [left/right extensions](../src/core/aa_ungapped.rs#L21) repeatedly index sequence slices and matrix rows. The diagonal's power-of-two geometry offers a stronger bounded-index invariant than the AA backbone, but current assembly already reuses a checked diagonal cell: do not claim repeated checks for each field. Consider binding exact sequence spans and active DP-row slices once, preserving pointer-direction semantics and sentinels. Current [score-only DP](../src/core/blast_dynamic_align.rs#L436) selects a matrix row outside the cell loop, as C does; remaining cell accesses involve sequence indexing, matrix-column bounds and DP-array indexing. [Traceback DP](../src/core/blast_dynamic_align.rs#L201) also addresses arena blocks through checked indices.

   Final score-only DP has a 200-byte stack reservation versus 120 bytes C, and traceback 392 versus 152 bytes C. Static `%rsp` references are 140/100 and 266/165 respectively. This supports investigating register pressure and address calculation; it does not prove an allocator bottleneck. C's `BSearchContextInfo` remains a call while Rust ThinLTO inlines its binary search into two-hit processing, potentially lengthening live ranges. Blanket inline annotations can worsen spills. Risk is medium: changing span boundaries must preserve X-drop cutoffs, strict score ties, dynamic band growth and edit-script ordering.

3. **Reuse CBS matrix row storage instead of rebuilding it per alignment.** This is a concrete remaining memory-lifetime difference, with unmeasured speed impact. [s_redo_one_alignment](../src/core/blast_kappa.rs#L477) converts the flat adjusted 28×28 matrix into 28 newly allocated row vectors for every alignment; [final identity setup](../src/protein_redo.rs#L404) repeats row reconstruction per retained context. Original `blast_kappa.c:1899–1959` reuses its gap-alignment matrix pointers, and its score block points to the adjusted matrix. Keep the Rust row allocation in the existing per-search/thread owner and overwrite scores, or provide an equivalent matrix view. This preserves values and row access order while removing allocations/copies. The payload is only 3136 bytes per conversion, so allocator counts and whole-workflow timing should decide priority; historical profile samples do not identify this as a dominant cost. No new general arena dependency is needed.

4. **Treat flattening and SIMD as lower-confidence followups.** Flattening score matrices might simplify proofs and reduce row-descriptor loads, but C also allocates separate rows, and both DP implementations already hoist row selection. This is primarily a code-generation experiment, not restoration of a missing contiguous C payload. The supported ordinary AA scan/two-hit/DP sources contain no explicit SSE/AVX/NEON kernel or runtime CPU dispatch to restore. The gapped recurrence has loop-carried dependencies and exact traceback ties; a generic SIMD replacement would exceed this audit's 1:1 scope.

Original scanner output uses `NCBI_RESTRICT`; Rust's exclusive mutable output slice already supplies a unique borrow, so “Rust lacks restrict” is not an adequate explanation. The default scanner's indirect function callback also exists in C. Existing traceback arenas, diagonal aging and scratch reuse should remain intact. Verify any next change with original-C focused checks, the 25-case core smoke gate and 1259-HSP real full-precision core parity, then use a fresh profile and parent-coordinated paired timing. Cache/branch counter evidence is needed before calling the remaining gap a cache-miss or branch-misprediction problem.
